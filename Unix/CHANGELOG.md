## [Unreleased]

### Added

- **`Configure-NpmConfig` (Bootstrap step `NpmConfig`) writes a GitHub token into `~/.npmrc` for private npm registries, the npm twin of `Configure-NuGetConfig`.** Nothing set up npm for GitHub Packages, so `npm install` of a private scoped package failed with `E401` until a token was added by hand, and the usual way, `npm config set //npm.pkg.github.com/:_authToken TOKEN`, leaves the token in npm's debug log. The new `npm.conf` names the `npmrc` (default `~/.npmrc`) and one `registry URL [SCOPE]` line per registry (the base ships `https://npm.pkg.github.com/`; the last line of a URL wins, so an overlay adds a scope). A registry whose `_authToken` line has a value and whose scope line matches is left alone; otherwise, or with `--override`, the token is asked once on the terminal and written for every registry that needs it, every other npmrc line kept in its place, the file owner-only and backed up into `Backups/Unix/System/NpmConfig/` first with every credential value replaced by `<redacted>`, so the undo never holds a token. The token never reaches another program, a log or the output. The step is off by default (it asks on the terminal) and runs right after NuGetConfig. Covered by `Unix/tests/modules/Bootstrap/Configure-NpmConfig.bats`; documented in the Bootstrap module reference, a new Configure-NpmConfig guide, Bootstrap a Mac, Configuration, Backups, Troubleshooting and the FoundationConfigurator.
- **`Upgrade-All` keeps Homebrew's pins in step with a new `package-pins.conf`, the `Version` column of WinuX's app lists.** Pins were only ever made by hand and Upgrade-All just listed them, so nothing in the repository said which formulae were held or why, and a pin outlived the decision behind it. One `brew FORMULA` line per formula to keep (`@TYPE` and the `.local.conf` overlay apply; the base ships none). Before `brew upgrade` Upgrade-All now reconciles both directions, as WinuX's `Sync-AppPins` does: an installed formula with a line is pinned (`brew pin`), and a formula of the bundled Brewfiles (the `brewfile` lines of `bootstrap.conf`, else `Unix/Brewfile` and `Unix/Brewfile.local`) that is pinned without a line is unpinned. A pin on a formula no Brewfile names was made by hand and stays; a line for a formula not installed yet is reported and pinned once it is. When the pins cannot be read or set the Homebrew upgrade is skipped and the run fails, since it would move a formula that should stay; before, a failed `brew list --pinned` was read as no pins. Homebrew pins the installed version and cannot pin a cask. The reconciliation lives in the new `Unix/lib/pins.sh`, keyed by package manager so another one that can pin joins with a line kind of its own. No time limit is put on the brew calls: unlike WinuX's `choco pin list`, none has been seen to stall, and `brew pin` and `brew list --pinned` only read and write the local Cellar. Covered by `Unix/tests/modules/System/Upgrade-All.bats`, `Unix/tests/pins.bats` and `Unix/tests/vanilla.bats`; documented in the System module reference, the Upgrade-All guide, Configuration, the software list and the overview.

### Security

- **`Configure-NuGetConfig` no longer keeps a token in its backup, and both token prompts refuse an answer with whitespace in it.** The backup taken before an existing `NuGet.Config` is rewritten was a full copy, `ClearTextPassword` included, so every rerun left one more plaintext copy of the old token in `Backups/Unix/System/NuGetConfig/` for the retention to keep. The copy is now made with every `ClearTextPassword` and `Password` value replaced by `REDACTED` (either attribute order), in a private temporary folder removed afterwards; the sources and every other line survive, and the token is asked again anyway. A token answer with whitespace in it is asked again, in `Configure-NuGetConfig` and `Configure-NpmConfig`: GitHub tokens have none, and a command pasted together with the token was otherwise written into the config as the token. Covered by `Unix/tests/modules/Bootstrap/Configure-NuGetConfig.bats` and `Configure-NpmConfig.bats`; documented in the Bootstrap module reference, the Configure-NuGetConfig guide and Backups.

## [0.2.1] - 2026-10-28

### Fixed

- **`Merge-Upstreams --dry-run` lists exactly what the merge would do.** It listed everything the upstream changed since the last merge, so a fork that already had a change saw paths "taken" and "declined" that the real run never touched, and it could not say which conflicts the real run would stop on. It now has `git merge-tree` (git 2.38 or newer) compute the same merge, with the same attributes and merge drivers, into a tree of its own, touching neither the index nor the working tree. It lists the paths that tree changes against HEAD: what the real run would take, what it would put back (a conflict there included, since putting back resolves it), and the conflicts it would stop on. The mirror drift warning now means what it says: a mirror file whose merged copy would differ from the upstream's. Covered by `Unix/tests/modules/Git/Merge-Upstreams.bats` (the dry run is checked against the real run); documented in the Git module reference, its guide and the Fork Model.
- **No workflow job runs in a private repository.** The `Mirror contract` job of `foundation.yml` and the `foundation-release.yml` job now carry the guard the macOS test job already had (`if: ${{ !github.event.repository.private }}`), so a private fork that merges Foundation starts none of Foundation's jobs and spends none of its Actions minutes on them. Foundation itself is public, where nothing changes. Documented in the Fork Model.

## [0.2.0] - 2026-10-28

### Added

- **`Update-Repositories --quiet` lists the stashes each repository holds.** A stash left behind (a restore that conflicted, one made by hand and forgotten) was invisible in the compact form the startup update prints. Under a repository's line, `--quiet` now prints `* Stashes =>` one tab in and every `git stash list` entry (`* stash@{0}: On master: MyStash`) two tabs in, all in white, with a blank line before the next repository; a repository without stashes prints nothing extra. Only a folder that is the top of its own repository is asked (`git rev-parse --show-cdup`), so a path inside another repository or an archive copy never shows the enclosing repository's stashes, and repositories not cloned, not configured or not a repository are skipped. Without `--quiet` nothing changes. The port of WinuX 1.9.0. Covered by `Unix/tests/modules/Git/Update-Repositories.bats`; documented in the Git module reference.

### Changed

- **`Update-Repositories --quiet` colors every repository line, and the totals counts, by bucket: updated green, up to date white, need attention red, skipped yellow.** Before, every line but one needing attention was green and the totals used another palette (updated blue, up to date green), so an updated repository did not stand out from an up-to-date one. Every line now starts with `=>`; one needing attention goes through `log_error` (red, on stderr, still shown at the quiet log level) instead of `log_warning`, a skipped one is yellow, an up-to-date one white. The line text, the buckets, `repo_format_result` and the totals text are unchanged. The port of WinuX 1.9.0. Covered by `Unix/tests/modules/Git/Update-Repositories.bats`; documented in the Git module reference.
- **`macos-configurator` is now `foundation-configurator`, and it configures both halves of a two-upstream fork.** The protocol page moves from `docs/unix/macos-configurator.md` to `docs/unix/foundation-configurator.md` (heading FoundationConfigurator, the twin of WinuX's WinuXConfigurator) and the product skill from `AI/Skills/foundation/macos-configurator/` to `AI/Skills/foundation/foundation-configurator/`: `/foundation-configurator` in Claude Code, `$foundation-configurator` in Codex CLI. The next `Deploy-AiArtifacts` run prunes the dangling `macos-configurator` link and links the new name; `exclude skills/foundation/foundation-configurator` leaves it out. A new ground rule (8), with a file-to-key table, has the session write the Windows counterpart of every entry it writes into `Configuration.local.psd1` (a layout into the Windows layout file) when `Windows/PowerShell/Configuration.psd1` exists in the checkout, following WinuX's protocol for the base file, the merge direction and the backup, reusing the Unix answers and asking only what Windows cannot share; Step 0 detects the other half and says so before the first question, and the closing summary lists the counterpart writes. A checkout of Foundation alone is unchanged: nothing is written and no folder is created. `Unix/tests/guides.bats` checks the renamed page. Documentation and skill text only: no command, configuration line or Bootstrap step changed.

### Breaking

- **Foundation lives in its own rooms: project documents move into `Unix/`, the docs into `docs/foundation/`, and `Merge-Upstream` becomes `Merge-Upstreams`.** A fork can now merge any number of projects (Foundation, WinuX, later ones) into one repository, with one command per project and no conflicts in the routine case. `CHANGELOG.md`, `CONTRIBUTING.md`, `VERSIONING.md`, `SECURITY.md`, `AGENTS.md`, `CONTEXT.md`, `NOTICE` and `THIRD-PARTY-LICENSES.md` move to `Unix/`; the root files of those names are generic pointers, the same bytes in every project. `docs/unix/` moves to `docs/foundation/`, so every published Foundation docs URL changes once (`#/unix/...` becomes `#/foundation/...`); the root docs landing and `docs/index.html` are generic hallway files. `Merge-Upstream REMOTE [--owned-only | --all-paths]` is renamed and generalised to `Merge-Upstreams NAME [--branch BRANCH] [--dry-run]`: it finds the remote by the manifest's URL (else by name; a missing one is printed as `git remote add NAME URL`), fetches only the project's prefixed tags, and handles every changed path by one rule - another project's rooms declined, the project's own rooms (`own`) taken, a fork's `take` line taken, a `mirror` file taken, the hallway taken only when the project is the root owner (`root-owner` of the new optional `Git/upstreams.local.conf`; default the only upstream, else `fork`) - then prints the declined paths, the suggested commit message (the newest release of the project's changelog) and the push command. It never commits, pushes or writes git config. The manifest `Unix/config/upstream.conf` is reshaped to plain `name`, `url`, `tag-prefix`, `changelog`, `own` and `mirror` lines (no `@TYPE`, no `upstream.local.conf` overlay); the `owned-only` line kind is dropped. The workflows are renamed `.github/workflows/foundation.yml` (the tests, formerly `unix.yml`) and `foundation-release.yml` (new): on every push to `master` it reads the newest `## [x.y.z]` heading of `Unix/CHANGELOG.md` and, when the tag does not exist yet, creates `foundation/vx.y.z` and the GitHub release. Tags are prefixed from now on (`foundation/v0.1.0`), so the tags of two upstreams never clash in a fork. `testrun_changelog_path` (the contract gate and `Run-Tests --update-contract-baseline`) reads `Unix/CHANGELOG.md`, so the check also runs inside a fork of several projects. Covered by `Unix/tests/modules/Git/Merge-Upstreams.bats` (real throwaway repositories), `contract.bats`, `doclinks.bats` and `guides.bats`; documented in the Git module reference, its configuration guide, Configuration and the rewritten Fork Model page.

### Fixed

- **A stalled zsh-autocomplete completion no longer leaves a zsh behind that fills RAM and swap.** zsh-autocomplete's async completion forks a worker shell and a zpty helper in its own session; once a completion stalls after its first redraw, nothing in the plugin stops the pair (its timeout covers only the first byte, `zasync cancel` only closes the pipe, and the helper never gets the terminal's SIGHUP), so a closed tab could leave a worker reparented to PID 1 whose helper's fork kept growing until the kernel killed it for low swap. `Unix/shell/autocomplete-guard.zsh`, sourced by `shellrc.sh` right after the plugin, wraps the worker start with a watchdog that kills the helper's process group and the worker after 10 s, exits on its own once the worker finishes (so a reused PID is never killed), and does nothing without the plugin. Covered by `Unix/tests/autocomplete-guard.bats`; troubleshooting entry "A leftover zsh fills RAM and swap". Reported upstream as marlonrichert/zsh-autocomplete#909.

- **A workspace window still resizing is no longer placed as if it had settled when the wait runs slowly.** `layout_wait` (Set-WorkspaceWindowLayout's wait) counts a window as ready once its title and its frame have held for `stable-ms`. Its first frame read was recorded without restarting the clock and could make the window ready at once, so when a pass took longer than `stable-ms` (a busy Mac, the 3-CPU CI runner) a window restoring its bounds, VS Code above all, was declared ready on a frame seen only once. A frame now needs a second matching read, at most one more poll. Covered by a new `layout.bats` test with a slow window-list read, which fails on the old code.
- **CI is faster and runs once per pull request.** The doc-link check computes each page's anchors once instead of once per link (145 s to a few seconds on the runner), and the `Unix` workflow runs on pull requests and on pushes to `master` only, not again for every push to a pull request's branch.
- **The Fork Model's two-upstream setup no longer breaks on tags.** Branches stay under each remote's name, but a clone keeps every tag in one namespace and both WinuX and Foundation tag `v0.1.0` and up, so a fork of both had every Foundation fetch refuse to overwrite WinuX's tags of the same name (and `Merge-Upstream`, which fetches first, stopped there). The one-time setup now keeps each upstream's tags under a prefix, `winux/v1.7.0` and `foundation/v0.1.0` (`--no-tags` plus a `+refs/tags/*:refs/tags/<prefix>/*` refspec per remote), and ends with a check: no bare tag left, both prefixes listed, `Merge-Upstream macupstream --dry-run` up to date. The `Merge-Upstream` guide points at it. Documentation only.

## [0.1.0] - 2026-10-25

### Added

- **Foundation, the macOS counterpart of WinuX, as its own repository.** The first public release of the Unix half that grew inside a fork of WinuX: bash executables in `Unix/modules/<Module>/bin` with the WinuX command names and aliases (`Open-Workspace` and `w`, `Close-Workspace` and `cw`, `Kill-All`, `Open-Browser` and `b`, `Update-Repositories`, the git shorthands), sourced libraries in `Unix/lib` with every AeroSpace, WezTerm and browser call in a driver, small per-concern config files in `Unix/config` with `.local.conf` overlays and `@TYPE` machine-type lines, chezmoi link templates in `Unix/home`, the `Unix/bootstrap.sh` first run handing over to `Bootstrap` and its switchable steps, the AI artifacts, marketplace and MCP server deployment, and the Custom area for a fork's own commands. The base config ships the `Test` machine type and generic values only.
- **`Merge-Upstream` (Git module) and `Unix/config/upstream.conf`.** Merges an upstream remote and stops before the commit; with `--owned-only` it takes only the paths Foundation owns, so a fork of both WinuX and Foundation takes each half from its own upstream. See the Fork Model page.
- **Tests and CI.** One bats suite per command, the library suites, the docs and guide gates, shellcheck and shfmt, run by `Run-Tests` and by the `Unix Tests` check on macOS.
- **Documentation.** The docsify site under `docs/unix/`: the getting-started overview, a man-style page per module, a configuration guide per command, configuration, bootstrap, workspaces, AI, software, backups, troubleshooting, the fork model and the roadmap.
