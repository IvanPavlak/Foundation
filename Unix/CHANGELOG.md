## [Unreleased]

### Added

- **Repository policies: a trust level per repository for AI agents, enforced by one hook (the Foundation half of WinuX 2.4.0).** An AI profile in `ai-profiles.conf` takes new lines: `policy LEVEL PATTERN...` (repeatable; the last matching line wins), `default-policy LEVEL` for every other repository and a folder without `origin` (default `branch`, today's behaviour) and `merge-without-checks PATTERN...` for `autonomous` repositories that may merge with no CI check reported; `autonomous PATTERN...` stays as a synonym of `policy autonomous`. The levels are a closed set: `autonomous` (also `gh pr merge` when every CI check of the pull request passed), `branch` (commit, push a feature branch, open and ready pull requests), `draft` (draft pull requests only), `readonly` (no Bash or PowerShell call and no file edit) and `blocked` (no work). Every level denies default-branch pushes, force pushes, branch deletion and remote, upstream and git configuration changes. A `policy` line naming no level is warned about and skipped, and a `default-policy` that is not a level becomes `readonly`. The engine hook `AI/Hooks/ai-repository-policy.sh` (a mirror file WinuX ships at the same path, new `mirror` line in `upstream.conf`) is deployed by `Deploy-AiArtifacts` next to the managed settings copy and wired into `PreToolUse` with matcher `*`; `ai-profile.conf` gains `default-policy`, `policy <level> <pattern>` (in file order) and `merge-without-checks` lines. The hook matches a command with prose taken out (a heredoc fed to `cat` or `-F -`, a quoted value with whitespace given to `-m`, `--title`, `--body` and the other message options), so a commit message that mentions git commands is not mistaken for one. `ai-ownership-guard.sh` refuses a `blocked` repository, and an unattended run (the launcher sets `AI_UNATTENDED`) when the profile has `unattended off` or the repository is at `draft` or `readonly`. `Test-AiProfile` lists the default level, every pattern with its level and the no-CI merge patterns (informational), and `Test-ConfigurationSchema` reports a `policy` or `default-policy` line naming no level. Tests: the new `ai-repository-policy.bats` (the policy matrix over every level, fed hook JSON; passes under `/bin/bash` 3.2 and bash 5 with the BSD tools), and the `aiprofile`, `Deploy-AiArtifacts`, `Test-AiProfile` and `Test-ConfigurationSchema` suites. Docs: [AI on a Mac - Repository policies](../docs/foundation/ai.md#repository-policies), the configuration reference, the AI module reference and guides, and FoundationConfigurator.
- **AI profiles: `Unix/config/ai-profiles.conf` names the one profile each machine runs, and `Test-AiProfile` checks it.** A `plan` line without a valid UUID fails closed: the managed settings copy is not rendered and the deployed one keeps its pin. Nothing pinned the Plan Claude Code is signed in to, and machine types (a layout choice) could not pick which rules, artifacts and MCP servers a machine gets. A profile is a `[Profile]` section with `rules NAME`, `plan NAME UUID...`, `deploy HARNESS...`, `include`/`exclude KIND/NAME...`, `mcp NAME...`, `marketplaces NAME...`, `unattended on|off`, `owns PATTERN...`, `autonomous PATTERN...` and `env NAME...` lines; before the sections, `host NAME PROFILE`, `default PROFILE`, `shared PATTERN...` and `default-owner PROFILE`. Every AI command picks the profile once (`FOUNDATION_AI_PROFILE`, then the host line, then the default; one resolver in the new `Unix/lib/aiprofile.sh`): `Deploy-AiArtifacts`, `List-AiArtifacts` and `Update-AiArtifacts` take its harnesses, rules item, includes and excludes, `Deploy-AiMcpServers` its servers, `Deploy-AiMarketplaces` its marketplaces. With no section (the base ships none) profiles are off and every command behaves as before, `@TYPE` forms included. The new `Test-AiProfile` prints the profile and how it was picked, the expected and the logged-in Plan (`oauthAccount` of `~/.claude.json`), whether the deployed managed settings pin it, every pay-per-use credential (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN` in the process, launchd, `/etc` and the shell profiles; `apiKeyHelper` in any Claude settings file) and the OAuth MCP servers; it exits 0, 1 on a mismatch, 2 without profiles. `Test-ConfigurationSchema` checks the new file. Covered by `Unix/tests/modules/AI/Test-AiProfile.bats`, `Unix/tests/aiprofile.bats` and the AI command suites; documented in AI on a Mac, Configuration, the AI module reference and the Test-AiProfile guide.
- **`Initialize-AiProfile` walks a machine's one-time sign-ins.** Once per machine after Bootstrap: it names the profile's Plan and offers `claude` for `/login` when the sign-in is not that Plan's, offers `gh auth login` when the GitHub CLI is signed out, lists the OAuth MCP servers and offers `claude` for `/mcp`, reports which of the profile's `env` variables are set, then runs `Test-AiProfile`. Every sign-in happens in the tool itself; nothing here reads or stores a secret. Covered by `Unix/tests/modules/AI/Initialize-AiProfile.bats`; documented in the AI module reference and the Initialize-AiProfile guide. The new Bootstrap step `AiProfileInit` (off by default, *interactive*) runs it right after `AiMcpServers`, so the Plan pin is deployed before the login is checked and a fresh Mac ends the run signed in; without a profile it is skipped with a warning. It waits at the terminal, so a run with it off stays unattended and, with a profile active, only warns and names `Initialize-AiProfile`. Covered by `Unix/tests/modules/Bootstrap/Bootstrap.bats`; documented in Bootstrap a Mac, the Bootstrap and AI module references, AI on a Mac and the Initialize-AiProfile guide.
- **Checkout and manifest sources in `ai-artifacts.conf`.** A section with `checkout PATH` links a local repository's items in place (its kind lines name the folders, `skills skills` without one), so a pull updates them at once; a section with `manifest FILE` reads a tab-separated manifest (name, kind, scope, source, ref, path, install) whose rows are cloned at their pinned commit once into `~/.local/share/foundation/ai-manifests/<owner>/<repo>/<ref>/` (by `Deploy-AiArtifacts` before it links, so Bootstrap's AiArtifacts step works on a fresh machine, not under `--check`, a failed fetch a warning, each fetch logged as it starts and run with git's prompt off so a private upstream fails instead of waiting; and by `Update-AiArtifacts`, whose `--check` reports pins behind their upstream default branch; the fetch code is shared in `Unix/lib/artifacts.sh`) and linked from there: `rename=` and `strip-invocation-guard` link a derived copy in the cache (the frontmatter `name:` set to the new name, since Claude Code names a skill by it, or `disable-model-invocation` removed), rows outside the AI profile's scope are skipped, and a `repo:NAME` row is linked into that repository's `.claude/skills/` (found by name in `repositories.conf`) with its link name in the repository's `.git/info/exclude`. `List-AiArtifacts` heads each source with its kind. Covered by the AI command suites and `Unix/tests/aiprofile.bats`; documented in AI on a Mac and Configuration.
- **`Configure-DockerDesktop` (Bootstrap step `DockerDesktop`) sets where Docker Desktop installs its command-line tools, from a new `cli-install system|user` line of `docker.conf`.** In user mode Docker Desktop links its tools into `~/.docker/bin` and, at every start, writes a PATH block into `~/.zprofile` and `~/.bash_profile`; the latter is a link into the repository, so the block (with the user's home path) landed in the tracked `Unix/shell/bash_profile` again after every fix. System mode links the tools into `/usr/local/bin` and writes into no shell profile. The command writes `DockerBinInstallPath` of Docker Desktop's `settings-store.json` with `plutil`, only when it differs: a running Docker Desktop is stopped first (cleanly, as `Open-Docker --stop`) and started again after, and the file is backed up into `Backups/Unix/System/DockerDesktop/`. Without a `cli-install` line (the base ships none) nothing changes; a Docker Desktop that never ran has no settings yet, which is a warning. The step is off by default and runs after NpmConfig. Covered by `Unix/tests/modules/Bootstrap/Configure-DockerDesktop.bats`; documented in the Bootstrap module reference, a new Configure-DockerDesktop guide, Bootstrap a Mac, Configuration, Backups and the FoundationConfigurator.
- **`Configure-NpmConfig` (Bootstrap step `NpmConfig`) writes a GitHub token into `~/.npmrc` for private npm registries, the npm twin of `Configure-NuGetConfig`.** Nothing set up npm for GitHub Packages, so `npm install` of a private scoped package failed with `E401` until a token was added by hand, and the usual way, `npm config set //npm.pkg.github.com/:_authToken TOKEN`, leaves the token in npm's debug log. The new `npm.conf` names the `npmrc` (default `~/.npmrc`) and one `registry URL [SCOPE]` line per registry (the base ships `https://npm.pkg.github.com/`; the last line of a URL wins, so an overlay adds a scope). A registry whose `_authToken` line has a value and whose scope line matches is left alone; otherwise, or with `--override`, the token is asked once on the terminal and written for every registry that needs it, every other npmrc line kept in its place, the file owner-only and backed up into `Backups/Unix/System/NpmConfig/` first with every credential value replaced by `<redacted>`, so the undo never holds a token. The token never reaches another program, a log or the output. The step is off by default (it asks on the terminal) and runs right after NuGetConfig. Covered by `Unix/tests/modules/Bootstrap/Configure-NpmConfig.bats`; documented in the Bootstrap module reference, a new Configure-NpmConfig guide, Bootstrap a Mac, Configuration, Backups, Troubleshooting and the FoundationConfigurator.
- **`Upgrade-All` keeps Homebrew's pins in step with a new `package-pins.conf`, the `Version` column of WinuX's app lists.** Pins were only ever made by hand and Upgrade-All just listed them, so nothing in the repository said which formulae were held or why, and a pin outlived the decision behind it. One `brew FORMULA` line per formula to keep (`@TYPE` and the `.local.conf` overlay apply; the base ships none). Before `brew upgrade` Upgrade-All now reconciles both directions, as WinuX's `Sync-AppPins` does: an installed formula with a line is pinned (`brew pin`), and a formula of the bundled Brewfiles (the `brewfile` lines of `bootstrap.conf`, else `Unix/Brewfile` and `Unix/Brewfile.local`) that is pinned without a line is unpinned. A pin on a formula no Brewfile names was made by hand and stays; a line for a formula not installed yet is reported and pinned once it is. When the pins cannot be read or set the Homebrew upgrade is skipped and the run fails, since it would move a formula that should stay; before, a failed `brew list --pinned` was read as no pins. Homebrew pins the installed version and cannot pin a cask. The reconciliation lives in the new `Unix/lib/pins.sh`, keyed by package manager so another one that can pin joins with a line kind of its own. No time limit is put on the brew calls: unlike WinuX's `choco pin list`, none has been seen to stall, and `brew pin` and `brew list --pinned` only read and write the local Cellar. Covered by `Unix/tests/modules/System/Upgrade-All.bats`, `Unix/tests/pins.bats` and `Unix/tests/vanilla.bats`; documented in the System module reference, the Upgrade-All guide, Configuration, the software list and the overview.
- **`shell.conf` takes WinuX's whole PSReadLine block: `edit-mode windows`, `key` handlers, `history-no-duplicates` and the two prediction options.** Line editing was configurable only for the history size and file and emacs or vi keys; every other behaviour was either hard-coded in the rc or missing. New line kinds, all zsh only: `edit-mode windows` (emacs plus the keys PSReadLine's Windows mode binds by itself, so far Home, End, Delete, Ctrl+Left and Ctrl+Right), `key KEY FUNCTION` with PSReadLine key names (`UpArrow`, `Shift+Tab`, `Ctrl+Spacebar`, `Ctrl+r`, `F2`, ...; each binds every sequence a terminal sends for it) or a raw `^` sequence, and PSReadLine function names (`HistorySearchBackward`, `MenuComplete`, `TabCompleteNext`, ...) or a zle widget name; a later line wins per key and `key KEY -` drops a binding, a `windows` one included, as `$null` does in `KeyHandlers`. `history-no-duplicates on|off` sets `HIST_FIND_NO_DUPS` (recall only, the file keeps every line, as `HistoryNoDuplicates`); `prediction-source none|history` and `prediction-view inline|list` are read and checked but not applied until the prediction part of the redo lands. The translation tables live in the new `Unix/lib/lineediting.sh`; `foundation-shell-settings` hands the rc finished `bindkey` lines, and `Test-ConfigurationSchema` now reports a `shell.conf` line the shell would skip (an unknown kind, key or function, a value its kind does not take). Covered by `Unix/tests/lineediting.bats`, `Unix/tests/modules/System/foundation-shell-settings.bats`, `Unix/tests/modules/Configuration/Test-ConfigurationSchema.bats` and `Unix/tests/shellrc.bats`; documented in Configuration, the Test-ConfigurationSchema guide, the Configuration module reference and the overview.
- **Tab, history saving and the prediction list now work as on WinuX, each a `shell.conf` line.** Measured against the WinuX capture (`Backlog/MacOS/Research/WinuXLineEditing.md`). `edit-mode windows` now also binds Tab and Shift+Tab to cycle through the completions in place, as PSReadLine's TabCompleteNext does: the first match goes in at once, the next Tabs cycle and wrap, with no list and no bell (`AUTO_LIST` and `LIST_BEEP` off). New lines: `completion-ignore-case on|off` (PowerShell always completes in any case); `history-save-style incrementally|at-exit|nothing` (PSReadLine's HistorySaveStyle: `incrementally` writes each line as it runs, so a new tab sees it at once, and every style but `nothing` skips a line equal to the one before it); and `prediction-source history` with `prediction-view list` now draw the prediction list, a Foundation widget in the new `Unix/shell/prediction-list.zsh` with no plugin and no background worker. From the first character it lists the history lines containing the typed text (any case, newest first, each once, at most 10 rows under a `<n/N>` header, every match highlighted); while it shows, Up and Down move in it and the line follows, otherwise they keep their own binding; Enter runs, Right keeps, Tab completes. Its look is configurable: `prediction-list-marker` (PSReadLine's `>` without a line) and `color-list-prediction`, `color-list-prediction-selected`, `color-emphasis` (PSReadLine's Colors; a name, 0-255 or `#RRGGBB`). The base ships none of these lines. Not ported, documented in the ticket: the Ctrl+Space menu, Esc, the other Windows keys, selection and clipboard keys, the inline view and F2, and the list showing another open tab's new lines live. Covered by `Unix/tests/prediction-list.bats`, `Unix/tests/lineediting.bats`, `Unix/tests/modules/System/foundation-shell-settings.bats` and `Unix/tests/shellrc.bats`; documented in Configuration and the overview.
- **The colours of `ls`, `ll`, `la` and `l` are configurable: `list-color KEY COLOR` in `theme.conf`, as Terminal-Icons themes the Windows listing.** eza always used its own colours. KEY is a friendly name (`directory`, `file`, `executable`, `symlink`, `user`, `user-other`, `group`, `group-other`, `date`, `size`, `size-unit`, `header`, `punctuation`, ...) or any two-letter key of `man eza_colors`, COLOR a name, 0-255 or `#RRGGBB`; foundation-shell-settings turns the lines into `EZA_COLORS`, which the shell rc's Icons stage exports, and a key without a line keeps eza's colour (the base sets none). `Test-ConfigurationSchema` reports a line with an unknown key or colour. Covered by `Unix/tests/lineediting.bats`, `Unix/tests/modules/System/foundation-shell-settings.bats` and `Unix/tests/modules/Configuration/Test-ConfigurationSchema.bats`; documented in Configuration, the Test-ConfigurationSchema guide and the Configuration module reference.

- **A workspace line ending in a lone `&` runs in the background (`Open-DBeaver &`), so the apps of an open start while its browser groups open.** Open-Workspace ran every action to its end before starting the next, so a workspace that starts VS Code, DBeaver, Obsidian and Mail waited for each before its first browser group. A marked action is started and the open goes on at once; it is waited for before the next `Set-WorkspaceWindowLayout`, `Focus-VirtualDesktop`, `Terminate-WindowsTerminalTabs` or `Return` and at the end of the workspace, so the layout and the ownership record still see every window. Only commands that just start apps, terminal tabs or containers may run in the background (`Open-Application` and every `Open-<App>`, `Open-Project`, `Open-ProjectTerminals`, `Open-VSCode`, `Open-VSCodeWorkspace`, `Open-Obsidian`, `Open-ClaudeDesktop`, `Open-Docker`, `Open-Acrobat`, `Start-Containers`); the browser openers take the window that appears after their own launch and so stay in place, and any other command marked `&` runs in place with a warning, which Test-ConfigurationSchema also reports. A background action cannot ask anything (a menu fails it instead of waiting), its output is shown when it is waited for, in colour when the open's is (the new `FOUNDATION_LOG_FORCE_COLOR`, which no launched app inherits), and its failure is named in the closing line like any other. Opt-in: a workspace without `&` opens exactly as before; WinuX has no equivalent. Measured with Measure-WorkspaceOpen (5 runs each), marking the app launches cut the median open from 12.3 to 9.4 s for a 6-window workspace and from 28.1 to 25.4 s for a 15-window one, every run faster than the fastest before, all placed at the first attempt. Covered by `Unix/tests/modules/Workflow/Open-Workspace.bats`, `Unix/tests/workspace.bats` and `Unix/tests/modules/Configuration/Test-ConfigurationSchema.bats`; documented in Configuration, the Workflow module reference and the Open-Workspace and Test-ConfigurationSchema guides.

### Changed

- **The `Unix Tests` check takes about a third of the time: the suites run as three shards side by side, the lint beside them.** The check took 10 to 13 minutes on most pull requests, 93-97% of it in the bats step, and the run is CPU-bound: Run-Tests already kept every core of the 3-CPU runner busy (the suites' summed time divided by the wall clock equals the CPU count), so only more runners make it faster. The workflow now runs three `Unix Suites (I/3)` jobs, each `Run-Tests --shard I/3 --audit-since ...` on its own macOS runner, and a `Unix Lint` job that runs shellcheck and shfmt on Linux (Homebrew's versions, as on a Mac); the required `Unix Tests` check is a small job that passes only when every shard and the lint passed, so the shard count can change without touching branch protection. Each shard uploads its run log as `unix-run-log-I`, installs only what the suites run (bash, bats-core, chezmoi; no Homebrew auto-update or cleanup) and stops Spotlight indexing first. The new `--shard I/N` of Run-Tests runs the I-th of N slices of the selection, split by the committed `Unix/tests/suite-weights.tsv` (each suite's time in a CI run; heaviest first onto the lightest slice, a suite without a weight at the median), so the shards end close together and every suite runs in exactly one; a shard is a scoped run and its `--audit-since` audits the suites it ran. `--update-suite-weights` rewrites the weights from the last suite times. The weights also order a first run's queue (CI has no `suite-timings.tsv`), longest first. Two slow checks got cheaper too: the docs link check computes each page's anchors in one pipeline instead of a few processes per heading and drops a `dirname` per link (5.8 to 0.85 s on an M5 Pro, every anchor of every page unchanged), and the Run-Tests suite's nested runs run one test of `match.bats` instead of all 27. Measured from PR #12's run, the split puts about 691 s of suite time on each of three runners where one carried 2073 s. Covered by `Unix/tests/testrun.bats`, `Unix/tests/modules/Tests/Run-Tests.bats` and `Unix/tests/doclinks.bats`; documented in the Tests module reference, the Run-Tests guide and the overview.
- **Arranging a desktop sends its AeroSpace commands in batches.** Every AeroSpace command was its own CLI call, about 17 ms of process start each, and a desktop's arrange made dozens: a native-full-screen check, a move and a tiling change per window, a move per parked window, the tree flattening, and the order walk (a focus move and a focused-window read per step). They now go through AeroSpace's `eval`, which runs a `;`-separated list in order as separate calls would (a failing command does not stop the next): one call for the full-screen checks, one for the parking, one for the moves, tiling and flattening, and two for the walk besides its first focus. A sentinel at the end of each batch tells a list that ran from one that did not, and then the commands go one by one as before, so an AeroSpace without `eval` arranges exactly as it did. Only plain tokens (window ids, workspace names) are batched. Measured with Measure-WorkspaceOpen (5 runs each), the arrange went from 9.6 to 5.8 s for a 34-window workspace, 5.9 to 4.2 s for a 15-window one and 1.9 to 1.35 s for a 6-window one, and the opens' medians from 20.4 to 16.8 s and 27.3 to 24.4 s, every window placed and verified at the first attempt. The AeroSpace stand-in of the suites runs `eval` (each command logged as its own call). Covered by `Unix/tests/modules/Window/Set-WorkspaceWindowLayout.bats` and `Unix/tests/layout.bats`.
- **The layout drawn at the end of a workspace's layout step takes about half as long.** Set-WorkspaceWindowLayout draws what it applied with Visualize-Layouts, which took 0.5 to 1.4 s: every zone lookup parsed `zones.conf` again (several processes each, for every desktop and window drawn or checked), each layout's entries were read again for every desktop, and `foundation_lower` started `tr` for every name it lowercased. `zones.conf` is now read once per process and read again when the config folder, the file, its overlay, `machines.conf` or the machine type changes (`conf_cache_key` in `lib/config.sh`, which the `apps.conf` cache now shares), the drawing reads a layout's entries once, and `foundation_lower` lowercases a plain name (ASCII letters, digits, space, dot, underscore, hyphen) in bash 4+ itself, other text still through `tr`. Output is unchanged: every layout of both layout sets with its project variants, the zone-set gallery and Test-ConfigurationSchema print byte for byte the same, every zone set and zone resolves the same, and `foundation_lower` gives `tr`'s result for all 4323 words of a personal config under the en_US, C, Turkish and Croatian UTF-8 locales in bash 3.2 and 5. The drawing went from 455 to 343 ms (6 windows), 1382 to 880 ms (15) and 1146 to 630 ms (34). Covered by `Unix/tests/layout.bats` and `Unix/tests/match.bats`.
- **Open-Browser notices each group's new window sooner.** It waits for every group's window before opening the next (a cold browser would otherwise merge the next group into it), checking every 0.25 s; it now checks every 0.1 s, with the same 20 s limit, so each group is handed on sooner (each check itself takes about 70 ms, so the cycle went from about 320 to 170 ms). Measured with Measure-WorkspaceOpen (5 runs each), the actions of an open dropped 0.1-0.2 s for 6-, 15- and 34-window workspaces, and the 15-window open's median from 27.4 to 26.8 s, every window placed at the first attempt. The 0.3 s pause after each group stays: it also keeps the layout from reading a window that is still loading. Covered by `Unix/tests/modules/Application/Open-Browser.bats`.
- **A workspace open's window matching no longer starts processes per window.** Every app lookup (`app_matches`, `app_role_members`, `app_bundle`, `apps_list`, ...) parsed `apps.conf` and its overlay again, several processes each, and `app_matches` runs for every window and layout entry on each poll of the layout wait, in Focus-VirtualDesktop and for every window the open records; a regex title match started one more process to translate its pattern. `apps.conf` is now read once per process and kept while the config folder, the contents of `apps.conf`, its overlay and `machines.conf` and the machine type variables are unchanged (a file written meanwhile is read again), roles are looked up without a subshell, the pattern translation assigns instead of printing, and Open-Workspace reads `kill-all.conf`'s keep apps once instead of per window. Answers are unchanged (compared on the shipped and a personal config and 3600 pattern/title pairs); one layout wait poll went from 195 to 60 ms (6 entries), 520 to 134 ms (34) and 985 to 205 ms (14). Measured with Measure-WorkspaceOpen (5 runs each), the median open went from 22.5 to 21.1 s for a 34-window workspace and from 29.4 to 28.1 s for a 15-window one, every run outside the other's range, with no run less placed than before; a 6-window workspace stayed within its own spread. Covered by `Unix/tests/config.bats`.
- **The `+managed-settings` destination is now a root-owned copy, never a link.** A link into the repository let anything that can write the repository loosen Claude Code's managed policy. `Deploy-AiArtifacts` renders the rules item's `managed-settings.json` (the token `{ManagedDir}` becomes the destination's folder; with an AI profile, `forceLoginOrgUUID` from its Plan and the ownership guard on `UserPromptSubmit` and `PreToolUse`) and writes it through sudo as `root:wheel`, mode 644, only when the content differs; next to it go the item's `hooks/` folder and, with a profile, `ai-ownership-guard.sh` (`AI/Hooks/ai-ownership-guard.sh`, a mirror file WinuX ships at the same path) and `ai-profile.conf`. Migration: nothing to change; the next deploy replaces the old link with the copy, and a source change needs a redeploy (`Deploy-AiArtifacts --check` reports a copy that differs).
- **Source precedence of the AI artifacts is fixed: `own`, checkout sources, `foundation`, `example`, vendored sources, manifest rows.** Before, `foundation`, `example` and the vendored sources were read together in name order, so a vendored source whose name sorts before `foundation` won a clash with the product skills. Migration: a fork that relied on a vendored item beating a `foundation` or `example` item of the same name excludes the losing one (`exclude skills/foundation/NAME`).
- **`Deploy-AiMcpServers` removes the servers it registered when the AI profile drops them.** With a profile, the servers registered per app are recorded in `$XDG_STATE_HOME/foundation/ai-mcp-servers.state`, and a recorded server the profile's `mcp` list no longer names is removed (`claude mcp remove --scope user`, its Codex table); a configured server an app already carries exactly as configured counts as registered, any other server is never removed. Without profiles servers are still only added and updated.
- **Deploy-AiMarketplaces takes the AI profile's `marketplaces` list**; `[plugin:NAME]` sections are always written.
- **The base `shell.conf` ships no setting, and the rc binds no key of its own.** Foundation enforces no line-editing behaviour: the base file documents the line kinds and sets nothing, so a fresh clone runs zsh's own defaults (history in `~/.zsh_history`, 4096 lines, emacs keys) and a fork chooses in `shell.local.conf`. The rc's hard-coded Home, End, Delete and Ctrl+Left/Right bindings are gone; they come from `edit-mode windows` or `key` lines. Migration: a fork that relied on the base's `history-size 4096` or `edit-mode emacs` keeps the same behaviour without them (both are the rc's fallbacks); one that wants the navigation keys back puts `edit-mode windows` (or the `key` lines it wants) in its `shell.local.conf`.

### Removed

- **The shell rc no longer enforces history, Tab-completion and prediction behaviour; it is being redone to match WinuX's PSReadLine, configurable through `shell.conf`.** The LineEditing stage had grown settings nobody could switch off: zsh-autocomplete with its history list as the default context (Tab then completed history lines too and could hang for minutes on a long path), zsh-autosuggestions, the arrow keys bound to its list or to prefix search, Enter running a highlighted entry, shared and deduplicated history (`SHARE_HISTORY`, `HIST_IGNORE_ALL_DUPS` and the rest), `menu select` and a case-insensitive matcher; in bash `HISTCONTROL=ignoreboth`, `histappend` and prefix search on the arrows. All of it is gone until each piece comes back as a `shell.conf` setting with WinuX's behaviour (Backlog/MacOS/51_LineEditingParity.md). What stays: `history-size`, `history-file` and `edit-mode` from `shell.conf`, `LANG`, interactive comments, the completion system started plainly (Docker's completions on fpath first), and zsh-syntax-highlighting (the Home, End, Delete and Ctrl+arrow keys stayed too, until they moved to `edit-mode windows`; see Changed). `Unix/shell/autocomplete-guard.zsh` stays but is not sourced. Migration: the `list-lines` line kind of `shell.conf` is gone (it sized zsh-autocomplete's list); delete it from a `shell.local.conf`, where it is now ignored. A fork that wants the old behaviour meanwhile puts the lines it misses in `~/.shellrc.local`, which runs after this stage.

### Fixed

- **The Unix suites no longer fail at random in CI on a stray "Broken pipe" error.** The GitHub Actions runner starts every job with SIGPIPE ignored, and bash cannot undo an ignore it inherited, so a builtin `printf` piped into a reader that exits early (`printf ... | grep -q`) printed `printf: write error: Broken pipe` on stderr now and then instead of ending quietly; `List-Functions.bats` caught it as unexpected output on a busy runner (7 of 100 runs of `List-Functions --list-discrepancies --quiet` under load, reproduced on a Mac with SIGPIPE ignored). `Run-Tests` now starts again through `perl` with SIGPIPE at its default when it finds it ignored (the run log names the reset), so CI runs every suite as a Mac terminal does; `List-Functions` looks a name up without a pipe, and its suite prints the unexpected output when that check fails.
- **Stopping Docker Desktop no longer ends in its "unexpected error" dialog.** `DockerWizard --stop`, `Open-Docker --stop` and Kill-All's Docker step quit Docker Desktop with an Apple Event (`quit app "Docker"`) after stopping the containers; on Docker Desktop 4.97 the VM then exited before the backend asked it to, Docker Desktop reported "the Docker Desktop VM stopped unexpectedly", offered Reset to factory defaults, and the stop waited until Quit was clicked. The quit now goes through Docker Desktop's own CLI, `docker desktop stop` (Docker Desktop 4.37 and later), which shuts the VM down on request and waits for it, bounded by `timeout stop`; the Apple Event quit stays for an older Docker Desktop, and the Docker Desktop process is still killed once `timeout stop` runs out. Covered by `Unix/tests/modules/Application/Open-Docker.bats` and `Workflow/DockerWizard.bats`; documented in the Application module reference and Configuration.
- **Docker Desktop's PATH block no longer sits in the tracked `bash_profile`.** In user mode Docker Desktop appends a block that puts `~/.docker/bin` on PATH to `~/.bash_profile` at every start, and that file is a link into the repository, so the block landed in `Unix/shell/bash_profile` (with the user's home path, above the file's shellcheck directive, which fails `Run-Tests`' lint). The shared rc now appends `~/.docker/bin` itself when it exists, once, for zsh and bash, `Unix/shell/bash_profile` carries no Docker block and says where an installer's lines belong (`~/.shellrc.local`), and Configure-DockerDesktop's system mode stops Docker Desktop from writing it. Covered by `Unix/tests/shellrc.bats`.

### Security

- **`Configure-NuGetConfig` no longer keeps a token in its backup, and both token prompts refuse an answer with whitespace in it.** The backup taken before an existing `NuGet.Config` is rewritten was a full copy, `ClearTextPassword` included, so every rerun left one more plaintext copy of the old token in `Backups/Unix/System/NuGetConfig/` for the retention to keep. The copy is now made with every `ClearTextPassword` and `Password` value replaced by `REDACTED` (either attribute order), in a private temporary folder removed afterwards; the sources and every other line survive, and the token is asked again anyway. A token answer with whitespace in it is asked again, in `Configure-NuGetConfig` and `Configure-NpmConfig`: GitHub tokens have none, and a command pasted together with the token was otherwise written into the config as the token. Covered by `Unix/tests/modules/Bootstrap/Configure-NuGetConfig.bats` and `Configure-NpmConfig.bats`; documented in the Bootstrap module reference, the Configure-NuGetConfig guide and Backups.

## [0.2.1] - 2026-10-28

### Fixed

- **`Merge-Upstreams --dry-run` lists exactly what the merge would do.** It listed everything the upstream changed since the last merge, so a fork that already had a change saw paths "taken" and "declined" that the real run never touched, and it could not say which conflicts the real run would stop on. It now has `git merge-tree` (git 2.38 or newer) compute the same merge, with the same attributes and merge drivers, into a tree of its own, touching neither the index nor the working tree. It lists the paths that tree changes against HEAD: what the real run would take, what it would put back (a conflict there included, since putting back resolves it), and the conflicts it would stop on. The mirror drift warning now means what it says: a mirror file whose merged copy would differ from the upstream's. Covered by `Unix/tests/modules/Git/Merge-Upstreams.bats` (the dry run is checked against the real run); documented in the Git module reference, its guide and the Fork Model.
- **No workflow job runs in a private repository.** The `Mirror contract` job of `foundation.yml` and the `foundation-release.yml` job now carry the guard the macOS test job already had (`if: ${{ !github.event.repository.private }}`), so a private fork that merges Foundation starts none of Foundation's jobs and spends none of its Actions minutes on them. Foundation itself is public, where nothing changes. Documented in the Fork Model.

## [0.2.0] - 2026-10-28

### Added

- **`Update-Repositories --quiet` lists the stashes each repository holds.** A stash left behind (a restore that conflicted, one made by hand and forgotten) was invisible in the compact form the startup update prints. Under a repository's line, `--quiet` now prints `* Stashes =>` one tab in and every `git stash list` entry (`* stash@{0}: On master: MyStash`) two tabs in, all in white, with a blank line before the next repository; a repository without stashes prints nothing extra. Only a folder that is the top of its own repository is asked (`git rev-parse --show-cdup`), so a path inside another repository or an archive copy never shows the enclosing repository's stashes, and repositories not cloned, not configured or not a repository are skipped. Without `--quiet` nothing changes. The port of WinuX 1.9.0. Covered by `Unix/tests/modules/Git/Update-Repositories.bats`; documented in the Git module reference.

### Changed

- **`Update-Repositories --quiet` colors every repository line, and the totals counts, by bucket: updated green, up to date white, need attention red, skipped yellow.** Before, every line but one needing attention was green and the totals used another palette (updated blue, up to date green), so an updated repository did not stand out from an up-to-date one. Every line now starts with `=>`; one needing attention goes through `log_error` (red, on stderr, still shown at the quiet log level) instead of `log_warning`, a skipped one is yellow, an up-to-date one white. The line text, the buckets, `repo_format_result` and the totals text are unchanged. The port of WinuX 1.9.0. Covered by `Unix/tests/modules/Git/Update-Repositories.bats`; documented in the Git module reference.
- **`macos-configurator` is now `foundation-configurator`, and it configures both halves of a two-upstream fork.** The protocol page moves from `docs/unix/macos-configurator.md` to `docs/unix/foundation-configurator.md` (heading FoundationConfigurator, the twin of WinuX's WinuXConfigurator) and the product skill from `AI/Skills/foundation/macos-configurator/` to `AI/Skills/foundation/foundation-configurator/`: `/foundation-configurator` in Claude Code, `$foundation-configurator` in Codex CLI. The next `Deploy-AiArtifacts` run prunes the dangling `macos-configurator` link and links the new name; `exclude skills/foundation/foundation-configurator` leaves it out. A new ground rule (8), with a file-to-key table, has the session write the Windows counterpart of every entry it writes into `Configuration.local.psd1` (a layout into the Windows layout file) when `Windows/PowerShell/Configuration.psd1` exists in the checkout, following WinuX's protocol for the base file, the merge direction and the backup, reusing the Unix answers and asking only what Windows cannot share; Step 0 detects the other half and says so before the first question, and the closing summary lists the counterpart writes. A checkout of Foundation alone is unchanged: nothing is written and no folder is created. `Unix/tests/guides.bats` checks the renamed page. Documentation and skill text only: no command, configuration line or Bootstrap step changed.

### Breaking

- **Foundation lives in its own rooms: project documents move into `Unix/`, the docs into `docs/foundation/`, and `Merge-Upstream` becomes `Merge-Upstreams`.** A fork can now merge any number of projects (Foundation, WinuX, later ones) into one repository, with one command per project and no conflicts in the routine case. `CHANGELOG.md`, `CONTRIBUTING.md`, `VERSIONING.md`, `SECURITY.md`, `AGENTS.md`, `CONTEXT.md`, `NOTICE` and `THIRD-PARTY-LICENSES.md` move to `Unix/`; the root files of those names are generic pointers, the same bytes in every project. `docs/unix/` moves to `docs/foundation/`, so every published Foundation docs URL changes once (`#/unix/...` becomes `#/foundation/...`); the root docs landing and `docs/index.html` are generic hallway files. `Merge-Upstream REMOTE [--owned-only | --all-paths]` is renamed and generalised to `Merge-Upstreams NAME [--branch BRANCH] [--dry-run]`: it finds the remote by the manifest's URL (else by name; a missing one is printed as `git remote add NAME URL`), fetches only the project's prefixed tags, and handles every changed path by one rule - another project's rooms declined, the project's own rooms (`own`) taken, a fork's `take` line taken, a `mirror` file taken, the hallway taken only when the project is the root owner (`root-owner` of the new optional `Git/upstreams.local.conf`; default the only upstream, else `fork`) - then prints the declined paths, the suggested commit message (the newest release of the project's changelog) and the push command. It never commits, pushes or writes git config. The manifest `Unix/config/upstream.conf` is reshaped to plain `name`, `url`, `tag-prefix`, `changelog`, `own` and `mirror` lines (no `@TYPE`, no `upstream.local.conf` overlay); the `owned-only` line kind is dropped. The workflows are renamed `.github/workflows/foundation.yml` (the tests, formerly `unix.yml`) and `foundation-release.yml` (new): on every push to `master` it reads the newest `## [x.y.z]` heading of `Unix/CHANGELOG.md` and, when the tag does not exist yet, creates `foundation/vx.y.z` and the GitHub release. Tags are prefixed from now on (`foundation/v0.1.0`), so the tags of two upstreams never clash in a fork. `testrun_changelog_path` (the contract gate and `Run-Tests --update-contract-baseline`) reads `Unix/CHANGELOG.md`, so the check also runs inside a fork of several projects. Covered by `Unix/tests/modules/Git/Merge-Upstreams.bats` (real throwaway repositories), `contract.bats`, `doclinks.bats` and `guides.bats`; documented in the Git module reference, its configuration guide, Configuration and the rewritten Fork Model page.

### Fixed

- **A stalled zsh-autocomplete completion no longer leaves a zsh behind that fills RAM and swap.** zsh-autocomplete's async completion forks a worker shell and a zpty helper in its own session; once a completion stalls after its first redraw, nothing in the plugin stops the pair (its timeout covers only the first byte, `zasync cancel` only closes the pipe, and the helper never gets the terminal's SIGHUP), so a closed tab could leave a worker reparented to PID 1 whose helper's fork kept growing until the kernel killed it for low swap. `Unix/shell/autocomplete-guard.zsh`, sourced by `shellrc.sh` right after the plugin, wraps the worker start with a watchdog that kills the helper's process group and the worker after 10 s, exits on its own once the worker finishes (so a reused PID is never killed), and does nothing without the plugin. Covered by `Unix/tests/autocomplete-guard.bats`; troubleshooting entry "A leftover zsh fills RAM and swap". Reported upstream as marlonrichert/zsh-autocomplete#909.

- **A workspace window still resizing is no longer placed as if it had settled when the wait runs slowly.** `layout_wait` (Set-WorkspaceWindowLayout's wait) counts a window as ready once its title and its frame have held for `stable-ms`. Its first frame read was recorded without restarting the clock and could make the window ready at once, so when a pass took longer than `stable-ms` (a busy Mac, the 3-CPU CI runner) a window restoring its bounds, VS Code above all, was declared ready on a frame seen only once. A frame now needs a second matching read, at most one more poll. Covered by a new `layout.bats` test with a slow window-list read, which fails on the old code.
- **CI is faster and runs once per pull request.** The doc-link check computes each page's anchors once instead of once per link (145 s to a few seconds on the runner), and the `Unix` workflow runs on pull requests and on pushes to `master` only, not again for every push to a pull request's branch.
- **The Fork Model's two-upstream setup no longer breaks on tags.** Branches stay under each remote's name, but a clone keeps every tag in one namespace and both WinuX and Foundation tag `v0.1.0` and up, so a fork of both had every Foundation fetch refuse to overwrite WinuX's tags of the same name (and `Merge-Upstream`, which fetches first, stopped there). The one-time setup now keeps each upstream's tags under a prefix, `winux/v1.7.0` and `foundation/v0.1.0` (`--no-tags` plus a `+refs/tags/*:refs/tags/<prefix>/*` refspec per remote), and ends with a check: no bare tag left, both prefixes listed, `Merge-Upstream macupstream --dry-run` up to date. The `Merge-Upstream` guide points at it. Documentation only.

## [0.1.0] - 2026-10-25

### Added

- **Foundation, the macOS counterpart of WinuX, as its own repository.** The first public release of the Unix half that grew inside a fork of WinuX: bash executables in `Unix/modules/<Module>/bin` with the WinuX command names and aliases (`Open-Workspace` and `w`, `Close-Workspace` and `cw`, `Kill-All`, `Open-Browser` and `b`, `Update-Repositories`, the git shorthands), sourced libraries in `Unix/lib` with every AeroSpace, WezTerm and browser call in a driver, small per-concern config files in `Unix/config` with `.local.conf` overlays and `@TYPE` machine-type lines, chezmoi link templates in `Unix/home`, the `Unix/bootstrap.sh` first run handing over to `Bootstrap` and its switchable steps, the AI artifacts, marketplace and MCP server deployment, and the Custom area for a fork's own commands.
